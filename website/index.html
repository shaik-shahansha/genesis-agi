Digital Beings Operating System

Autonomy you can audit.

Genesis runs persistent agents that own a workspace, remember across restarts, and act on your behalf. Every consequential action passes a deterministic policy engine — so it either waits for your decision, or it leaves a receipt you can verify.

The governed action path how a decision is made

Nothing consequential runs without a decision — and refusals are recorded too. A log that only shows successes cannot tell you what an agent tried to do.

The gap

Agents are easy to build and hard to trust

Give a model tools and a schedule and it will do something impressive. Then it will send an email it should not have, or run code you cannot inspect, and there is no record of why. Governance decides whether autonomy is usable at all.

Ungoverned agent

  • Permission is a prompt: "always ask before emailing"
  • Approval is a chat reply, lost with the conversation
  • Denials are invisible — only successes get logged
  • A tool description can talk the agent into anything
  • Tool code runs with your environment and your network
  • "It cannot be bypassed" — and then it is

Governed being

  • Permission is code, evaluated on the action's real parameters
  • Approval is a durable record bound to those exact parameters
  • Refusals are first-class events, carrying the rule that caused them
  • A model can raise the required control, never lower it
  • Untrusted code runs under CPU, memory and no-install limits
  • A broken control plane refuses rather than permits

Governance control plane

Six risk tiers, five dispositions, no model in the loop

The engine runs at the action boundary, not the prompt boundary — after the plan exists and before any capability fires. It is pure, so the same context always produces the same decision. Pick a tier.

What you would see

Invariants the test suite holds us to

Unknown capability

Floors at R3. There is no permissive default: forgetting to declare a capability gates it rather than freeing it.

Dangerous names

A capability whose name matches a harmful pattern is R5 even if nobody declared it. Physical names are at least R4.

Model advisory

A classifier may raise the required control. It can never lower it below what the deterministic rules demand.

Tenant ceiling

Organisation settings can pre-approve up to R2, scoped to named capabilities. R3 and above always need a human, and a blanket grant is ignored.

Payloads are redacted by the writer, before they are stored, so a caller cannot persist a secret by passing one in. Verification re-walks the chain and reports the first broken link — a missing receipt is itself an incident.

Status

What is real, and what is not

Most projects in this space describe an aspiration in the present tense. This table is generated from the same tracker the developers use, and it says partial and planned out loud.

And two claims we removed

"Violations cannot be bypassed via prompt injection"

It was a substring scan of the user prompt. Paraphrase, translation, or an instruction hidden in retrieved content walked straight past it. Enforcement moved to the action boundary; prompt screening is now labelled advisory.

"Consciousness"

The mechanism is a periodic cognition loop with awareness tiers and budget caps. Calling that consciousness made the whole project harder to take seriously.

Roadmap

Ordered by what blocks what

Phase B is a gate: nothing after it starts until the execution and governance path is closed. The remaining blockers are named rather than implied.

  1. A

    Discovery & deployment

    Reality matrix, threat model, dependency inventory. A single-container image that runs on a small VPS, non-root, verified with a smoke test.

    Done
  2. B

    Containment & governance the gate

    WebSocket authentication, path traversal, unbounded uploads and runtime installs are fixed and verified. Policy engine, approvals and the audit journal are built. Remaining: a container-isolated sandbox provider, real egress blocking, and MCP environment scrubbing.

    Nearly
  3. C

    Kernel extraction

    Split the ~99 KB Mind object into kernel, persona, capability, memory and cognition. This is what unlocks snapshotting, forking and multi-process daemons.

    Next
  4. D–F

    Journal as the timeline of record, memory V3, portable identity

    Wire the remaining write paths into the journal, add bi-temporal memory and hybrid retrieval, then signed, exportable identity.

    Planned
  5. G–K

    Durable autonomy, workspace, skills, voice, tenancy

    Suspend and resume on approval, a real workspace, an MCP and skills marketplace with per-skill risk, realtime voice, and organisational controls.

    Planned
  6. L–M

    Embodiment, then Genesis World

    A hardware abstraction with a safety-rated stop, and physical actuation as an R4 capability. Only once the governance plane has been stable for a while.

    Planned

Get started

One container, about a minute

The API, the web workspace and this site are served behind one nginx front door, so a small VPS is enough for a handful of Minds.

1

Configure

A real signing key is required — the compose file refuses to start without one — plus at least one model provider key.

2

Build and run

Multi-stage build, non-root at runtime, health-checked.

3

Open the workspace

Create a Mind, then open its Governance page. That is where decisions land.

bash 
# 1 · generate a signing key, then paste it into .env as API_SECRET_KEY
python -c "import secrets; print(secrets.token_hex(32))"

# 2 · build and run
cp .env.example .env
docker compose up -d --build

# 3 · open the workspace
# http://<your-host>:8080
